# ポートフォリオ用デモ環境の設計案

状態: 初期設計の記録。デモ開始・分離・回収・UI・migrationの実装仕様は
[ポートフォリオ用デモ](portfolio-demo.md) を正とする。
以下に残す候補テーブルやlease案などには、実装で調整した項目が含まれる。
実装順序は公開環境の保護 → デモ分離 → ドキュメント管理 → 検索・復元・監査画面。
未コミットのAI支援とVercel Eveへの移行検討は後続課題とする。

## 利用体験

ログイン画面の「デモを試す」で、訪問者ごとに架空の組織・ユーザー・Projectと
要件・タスク・テストのサンプルを作成する。共通パスワードを公開した共有ユーザーは使わない。
同じ訪問者の複数タブは同じデモに参加し、別の訪問者は別のデモを使う。

合意した公開範囲は通常業務と組織内の管理まで。
権限は `tenant_owner` とサンプルProjectの `project_admin`。
組織内ユーザー管理を含む通常機能を体験できるようにする。
公開利用者に `system_admin` を付与しない。
運営管理の疑似体験は初期範囲に含めない。

画面に「デモ環境」「入力はログアウト・期限切れで利用できなくなる」ことを表示する。
「最初から試す」で自分のデモを失効させ、新しいデモを開始する。
実名・実メールアドレス・機密文書を要求しない。メール送信は行わず、デモ内の通知で示す。
AI支援の外部呼び出しはこの段階では含めない。

初期案の期限は無操作15分、開始から最大60分。既存の通常セッションの期限は変更しない。
期限はBackendで判定し、ブラウザのタイマーは表示だけに使う。

## 現在のコードを使う境界

| 現在の構成 | デモで必要な追加 |
| --- | --- |
| `tenants` / `tenant_members` と所有経路によるORM制限 | セッションからデモのtenantを確定し、切り替えを拒否する |
| `users` は組織をまたぐIdentity | デモごとに専用の架空Identityを作り、既存利用者を再利用しない |
| `sessions` にidle・absolute expiry・失効理由 | デモ所有情報とcleanup状態を別テーブルで管理する |
| `projects` 配下の既存RBAC | 通常のpermission・Project所属検証を引き続き使う |
| アバターは利用者単位、pending uploadは `pending-uploads/{user_id}` | アバター・未登録ファイルもデモの専用prefixと所有情報に含める |
| 現在の直接送信許可は署名付きトークンで、DBの台帳がない | 発行した送信許可・キー・失効期限・予約容量をデモ側で記録する |

通常の認証処理にデモ状態の検証を加え、業務サービスを書き直さない。
認証直後に `demo_session → session/user/tenant` をサーバー側で確認する。
`X-Tenant-ID`、body中のID、URL中のID、profile/avatar、bulk・export・file経路を含め
別のデモや通常組織への到達を拒否する。UIの非表示だけで認可しない。

デモ中に作成したIdentityもすべて所有台帳に登録する。
既存Identityの検索・招待、通常のメール確認・パスワード再設定を通して
デモ外の利用者を参照・変更したり、通常アカウントとして再ログインしたりできないようにする。
存在するメールアドレスに対する作成・招待操作も、実アカウントの存在を返さない。
アプリ外の外部URLへのリンクは安全な表示に留め、サーバーが取得する機能は追加しない。

## DB変更案

`demo_sessions` に以下を持たせる。通常の `sessions` と切り離した別認証方式は作らない。

- UUID、専用tenant ID、開始者のuser ID、認証session ID（いずれも重複を禁止）
- 作成日時、idle/absolute期限、失効日時・理由
- 状態 `active / cleanup_pending / cleaning / cleaned`
- cleanupの試行回数、次回試行、lease期限、最終エラー種別
- 作成件数・予約容量などの使用量

`demo_owned_users` と `demo_uploads` で追加Identity、object key、発行済みPUTの
有効期限・予約バイト数を追跡する。直接送信の完了登録は生きたデモ所有情報も要求する。

既存利用者・既存組織の列と値は変更しない。新規テーブルをAlembicで追加する。
通常環境でデモAPIを有効にしない。公開用は `APP_ENV=demo` と専用DB・ストレージを使用する。
現段階の `APP_ENV=demo` は公開保護のみを有効にし、デモの作成・破棄はまだ動作しない。

専用DB/制限付きロール・非公開ストレージを、既存のPostgreSQL/S3互換API構成で用意する。
本番データを複製しない。無料枠に収まる配置を確認してから接続先を切り替える。

## 失効と削除

ログアウト・期限切れ・リセットでは最初に `active` を解除し、関連する認証sessionを
失効させる。以降のAPIはcleanupの成功を待たずに拒否する。認証済み応答をキャッシュしない。

失効と同時にcleanup対象をDBへ保存し、失効後に削除を試みる。
Vercelレスポンス後の未追跡バックグラウンド処理を成功条件にしない。
ブラウザが閉じられた場合はidle期限で利用を拒否し、定期処理が未削除デモを回収する。
HobbyのCronは1日1回を前提にするため、期限切れの物理回収は翌日になる場合がある。

cleanupはleaseで多重実行を抑え、失敗時は再試行する。台帳を先に削除しない。
Project配下をFK依存順に削除し、組織所属・draft・通知・業務監査内容・デモIdentityと
セッション・アバターも対象にする。既存FKは一括CASCADEを前提にせず依存関係を列挙する。
`roles` / `permissions` / 共通avatarなど共有マスタは削除しない。

S3互換ストレージではサンプルの共通read-onlyファイルと訪問者のファイルを分ける。
削除後にも発行済みPUT URLでobjectが再作成され得るため、最終PUT期限後にprefixを
もう一度走査・削除してから `cleaned` にする。保管期間・バージョニングも削除方針へ含める。

既に発行したGET URLはAPI sessionの失効だけでは止められない。
短いURL期限をsessionの残り時間以下に抑え、objectを削除する。
失効直後のダウンロード拒否が必要なら、認証を毎回確認する配信方式を採用する。

FrontendではデモUUIDごとのdraft/cache namespaceを使う。
logoutと認証失効時にReact Query、localStorage・IndexedDB中の入力下書き、upload stateを消す。
他タブへ失効を通知する。削除するのは当該デモの内容で、テーマ設定などは維持する。

ここで保証するのは期限切れ時のアクセス拒否と、追跡可能な再試行付き回収。
利用者がダウンロード済みの内容やDBバックアップからの即時消去は保証しない。
操作内容を含まない最小限のセキュリティ記録は別途短期保持し、通常の長期業務監査と分ける。

## 濫用対策の初期値案

既存のIP単位・全体のリクエスト制限に加え、匿名デモ開始を専用に制限する。
tenant作成前にDBの共有カウンター・全体容量を原子的に確保する。instance内だけで数えない。

| 項目 | 初期値案 |
| --- | --- |
| デモ開始 | 同一IPで1時間3回 |
| 同時デモ | 全体で10件 |
| 同じデモで作るProject | 3件 |
| 架空ユーザー | 10件 |
| 要件・タスク・テストなどの書込み | 合計500件を目安に対象テーブルごとに定義 |
| 訪問者のファイル | 合計20MB、1件5MB、10件 |

DB件数と容量はサンプル分も計上する。upload plan時にサイズを予約し、完了時に実体を
検証する。期限切れ許可の解放と実体の削除は別管理とする。
上限到達時は429/容量エラーで新規作成を止め、既存の参照は維持する。
free tierの実際の上限とsample seedのサイズを測って最終値を決める。

## API・検証・切り替え案

候補APIは `POST /demo/start`、`GET /demo/status`、`POST /demo/reset`。
start/resetは既存CSRF処理に組み込み、startの匿名操作でも送信元・CSRFを検証する。
cleanup専用入口は公開利用者の権限と分け、サーバー専用secretを確認する。
OpenAPI変更後はOrvalを再生成し、API guide・画面のエラー文言を更新する。

実装完了条件:

1. 同時に開始した2人のdemoが、読取・更新・bulk・export・avatar・ファイルで交差しない。
2. デモから通常Identity・通常tenant・運営管理へ到達できない。
3. logout/idle/absolute期限/reset後は旧cookieと旧tokenで操作できない。
4. DB削除失敗・S3削除失敗・Cron多重実行でも再試行でき、共有資源を消さない。
5. logout後の遅延PUTも最後の回収で削除する。
6. 新しいデモや別のブラウザに、以前のdraft/cacheが表示されない。
7. 同時開始・同時uploadで容量上限を超えず、DB障害時は上限検証を迂回しない。
8. 新規migrationを通常データ入りDBへ適用しても、既存Identityと認可が維持される。

公開切り替えは専用資源とサンプルseedを用意し、Backendを先に配信・境界確認し、
Frontendのデモ開始導線を配信する。現在のVercel接続先・環境変数はこの設計段階では変更しない。

## 次のドキュメント管理

現状は専用画面がplaceholderで、`document:read/create/update/delete` はRBACに定義済み。
要件管理の `requirement_documents` とは別のProject文書として追加する。
初期範囲はMarkdown本文と添付、revision履歴、一覧・検索、要件/タスク/テストへの関連付け。
現行のMarkdownTextarea、presigned upload、楽観ロック・監査・所有経路検証を再利用する。
文書・revision・添付もデモcleanup台帳に含め、作成と破棄を同時に検証する。
