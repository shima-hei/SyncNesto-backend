# Codex向けMCPの実装方針

## 合意した目的と境界

- AI支援・Eveへの移行は取りやめ。Codexが判断し、既存FastAPIが認可・検証・保存する。
- 初版はMac上のローカルHTTP MCP。Codex標準のOAuthでブラウザを開き、既存Syncnestoアカウントで接続を許可する。手動APIキー発行を標準導線にしない。
- 通常ユーザーは既存の通常DBを使う。デモDB・Storageへの切り替えや通常Cookie/BFF/CSRFの緩和はしない。初版のMCPは通常アカウントのみ。
- MCP独自のロールを複製しない。既存のProject permissionに`mcp:connect`を追加し、project_admin / manager / memberに付与する。
- guestは横断属性であり利用禁止の根拠にしない。編集権限のある外部協力者は利用可能。閲覧専用・テスト実行専用は対象外。
- 各操作で有効なユーザー・組織所属・Project所属・`mcp:connect`・操作permissionを検証する。組織管理者や運営者という理由で業務権限を迂回しない。
- 接続許可したProjectとOAuth scopeを上限とし、現在の権限との積集合で判定する。失効・所属解除・降格は次の操作で反映する。
- 操作主体は接続した本人。監査には`source=mcp`と接続識別子を記録し、トークンを含めない。

## 提供する操作

1. 要件定義の参照・作成と、文書/セクション/要件/フィールド/引用箇所を指定したレビューコメント。
2. テスト設計の参照・作成と、項目UUID・列、またはパターンUUID・因子UUID・水準UUIDで指定したレビューコメント。
3. タスク検索・起票・編集・状態/担当/日程/工数更新、要件との関連、親子タスク。
4. 依存関係・マイルストーンを利用した計画。複数件の日程変更は変更案を確認してから反映する。

レビューは1指摘=1コメント=1書き込み呼び出し。対象versionを検証し、古い箇所へ投稿しない。リトライ時の重複作成を防ぐ。全グラフの置換をモデルに任せず、追加はサーバーで最新データへ統合する。

要件は既存draft状態を使用する。テスト設計には現在draft状態がないため通常の設計として保存し、人が編集・確認できる形にする。休日・個人稼働率を推測で永続化しない。

## 認証の実装境界

- ローカルMCPは127.0.0.1限定。Host/Originを検証し、任意ネットワークへ公開しない。
- Authorization Code + PKCE S256、短命のアクセストークン、更新トークンのローテーションと失効を使用する。
- ブラウザ上の同意は既存Cookie/BFF/CSRFで保護し、認可コードは一回限り。リダイレクト先とresourceを許可リストで検証する。
- ローカルMCP向けトークンを通常APIへ流用しない。連携用APIでは用途を分離した資格情報と検証を用いる。
- OAuth discovery/tokenと連携APIのみ専用の直接経路を設け、通常APIのBFF必須を維持する。直接経路にも共有レート制限を適用する。
- 接続の一覧・取り消しを本人のアカウント画面から提供する。

## 実装・検証の順序

1. OAuth・接続管理・MCP利用permission・migrationとローカルHTTP接続。
2. 必要箇所を分割取得する参照ツール、指摘コメント、画面から指摘箇所へ移動する導線。
3. 要件・テスト設計の作成、タスク操作、日程案の確認・適用。
4. 権限境界、失効、古いversion、再試行、通常/デモ分離、既存機能の回帰確認。

## 実装結果

- 公式Python SDKによるローカルHTTP MCPと、FastAPI側のOAuth・連携APIを実装。ブラウザ同意・接続一覧・取消をFrontendへ追加した。
- 28ツールを提供する。既存のServiceと入力契約を利用し、接続した本人の現在の権限で要件・テスト設計・タスク・依存関係・マイルストーンを操作する。
- 閲覧専用・テスト実行専用は不可。編集可能なguestは可。接続時のProject許可を超えたアクセス、所属解除・降格・認証情報変更後のアクセスを拒否する。
- 要件コメントは版・フィールド・原文の引用位置を検証する。テスト設計コメントは未選択の水準セルもUUIDで特定する。既存の因子単位コメントは維持した。
- 要件の指摘箇所への移動と引用表示を追加。詳細画面にしかないフィールドへは詳細画面へ移動する。未決事項にもコメント・指摘を確認する導線を追加した。
- 書き込み・再送結果・監査を同じ外側のtransactionで確定する。既存Service内のcommit/rollbackで排他制御が失われないことを検証した。
- デモ破棄処理とORMの所有関係にMCP用4テーブルを登録した。通常データの保持とデモのログアウト・期限切れ時の破棄を回帰確認した。
- CIの検証環境・依存関係監査にはMCPのoptional extraを含める。公開Backendの実行にローカルMCP用SDKを必須にしない。

## 検証結果

- MCP関連33ケースを含む、MCP・デモ・入口制御の回帰テスト56件が成功。
- Backend全体875ケースを実行し、864成功・5skip・3既知xfail。残る3件は、本人単位の接続管理を組織選択APIと扱うテスト2件と旧migration headを固定したテスト1件だった。
- 接続管理の5経路を明示して本人認証Dependencyを検証し、migration headはAlembicの現在値から取得するよう修正。失敗した3件とmigration失敗時のrollbackの計4件を再実行し、4件成功。アプリコードを変更せずテストの前提を更新したため、全体の再実行はしていない。
- Backend Ruff・Pyright成功。MCP extraを含む固定依存関係の監査で既知の脆弱性なし。
- Frontend 71件成功。format・typecheck・lint・Production build成功。OpenAPIからOrvalコードを再生成した。
- ローカルのdevelopment / localhost / syncnesto DBを確認し、追加migration `91a7d2b8c406` を適用した。

## 現在の適用範囲と残作業

- 本体の各mainブランチで実装。既存のAI支援stashとInfraは変更していない。
- 実際の環境変数は変更しておらず、MCPは既定の無効状態。Codexへの登録・本人によるブラウザ同意・実際のCodexからの一連の操作は未確認。
- 公開環境へのpush・有効化は未実施。公開時は既存CIで通常DBと専用デモDBの両方へmigrationを適用してからBackendを配布する。通常ユーザーの接続先をデモへ切り替えない。
- 次はローカルでBackend/FrontendのMCPフラグを有効にし、MCPを起動、Codex標準OAuthで本人がProjectを許可して、要件・設計・タスク・指摘コメントの操作を確認する。起動手順は[docs/mcp.md](../mcp.md)。
- 期限切れの接続・認可要求・資格情報・再送結果を物理削除する定期保守処理は未実装。有効期限・失効によるアクセス拒否は実装・検証済み。
