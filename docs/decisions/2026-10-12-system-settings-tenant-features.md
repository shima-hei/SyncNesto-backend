# システム設定と組織ごとの機能許可

2026-10-12。設計書。以下のAPI・モデル・画面はまだ実装していない。
運営・組織・Projectの分離は[既存の決定記録](2026-10-10-mfa-authorization.md)を引き継ぐ。

## 確定した境界

- システム管理者は全体のユーザー・組織・システム設定・組織への機能許可を管理する。
- 運営Roleだけでは業務データの閲覧・更新を許可しない。所属とProjectのPermissionを別途要求する。
- 組織管理者は現在組織のメンバー・設定・Project作成を管理し、運営設定や機能許可を変更できない。
- 機能許可はRoleに権限を追加しない。許可されても本人に既存の業務Permissionが必要。
- 2026-10-12、ユーザーは「機能を無効化しても既存データの閲覧・出力を維持する」を選択した。
  作成・更新・削除・コメント・実行結果の記録・MCP経由の変更は停止する。保存データを削除しない。
  閲覧・出力にも現在の所属とPermissionを要求し、無効化によって閲覧範囲を広げない。
- 通常/デモのDB・Storage分離、通常全員のMFA、匿名デモの業務体験を維持する。

## 初版の対象候補

組織の許可一覧は固定の機能キーとして扱い、任意の文字列や自由なJSON設定を受け付けない。

| 候補キー | 対象 | 無効時 |
| --- | --- | --- |
| requirements | 要件定義・レビュー・指摘コメント・成果物リンク | 既存の閲覧/出力を維持。作成・編集・レビュー状態変更・コメント・リンク変更を停止 |
| tasks | タスク・依存関係・マイルストーン・日程変更 | 既存の閲覧/出力を維持。更新と日程案の保存・適用を停止 |
| test_designs | テスト設計・レビューコメント・要件リンク | 既存の閲覧/出力を維持。設計変更・指摘・リンク変更を停止 |
| test_execution | テストケース・実行記録・不具合との対応 | 既存の閲覧/出力を維持。ケース変更・結果記録・不具合作成を停止 |
| documents | ドキュメント・添付・復元 | 既存の閲覧/ダウンロードを維持。アップロード・更新・削除・復元を停止 |
| mcp | 外部クライアントの接続経路 | 新規接続と既存接続からの操作を停止。Webでの閲覧/出力は維持 |

上表は実装前に確定する候補であり、機能キーや細分化を導入済みと扱わない。
MCP自体の停止は接続経路の停止なので、MCP内のreadも停止する。
個別の業務機能だけを無効にした場合は、MCPでのreadは既存Permissionの範囲で維持し、writeを停止する。
監査ログ・メンバー管理・認証・復旧等は任意の業務機能として停止させない。

## 判定とAPIの案

業務操作の可否は、MFA済みの本人・有効な組織所属・Project所属・業務Permission・組織の機能許可の積で判定する。
MCPではさらに接続のProject同意範囲と現在の`mcp:connect`を要求する。
フロントエンドの非表示だけで制限せず、Backendの共通Dependency/Serviceで操作の種別ごとに強制する。

- システム設定は固定キー・型・許容範囲を定義し、バージョン付きで更新する。
  初版は機能の標準許可等を候補とし、何を画面で変更可能にするかは実装前に確定する。
  `APP_ENV`、`DEMO_MODE`、MFA必須設定、秘密鍵・接続情報はこの画面の編集対象に含めない。
- `system_setting:read` / `system_setting:update` / `tenant:feature_manage`を運営用Permissionの追加候補とする。
  組織Role・Project Roleへは付与しない。既存の6運営Permissionへ導入済みとは扱わない。
  導入時はseedの固定許可一覧と追加付与用の新しいmigrationを一緒に更新し、既存migrationは書き換えない。
- `/system/settings`、`/system/tenants/{id}/features`を候補とする。GETとPATCHを分ける。
  組織管理者向けは現在組織の許可状態を読み取るだけとし、全組織の設定を返さない。
- PATCHはversionによる排他制御、Cookie認証ならCSRF、更新前後の監査ログを必須にする。
  操作者・対象組織・機能キー・旧値・新値を記録し、秘密や不要な業務本文を含めない。
- 無効な機能への変更要求は`403 FEATURE_NOT_ALLOWED`等の専用コードで説明する。
  API/エラー契約は実装時にBackendとFrontendの仕様書・Orvalへ反映する。
- MCPのcatalogとexecuteの両方で現在の許可を確認する。idempotency receiptを返す場合も先に確認する。
  保存済み日程案を適用する時も再判定する。トークン発行時の状態だけを信用しない。
- 全面メンテナンスや侵害対応の緊急停止は今回の組織許可と分けて設計し、通常の機能無効化へ混ぜない。

## 画面の案

- 運営画面だけで機能許可を変更し、組織管理画面には現在組織の状態を読み取り表示する。
- 無効でも既存データへ移動できるメニューを残し、「閲覧のみ」と停止理由を表示する。
  新規作成・編集・コメント・復元等の操作を制限し、閲覧や出力の導線を一緒に隠さない。
- すでに開いている編集画面やMCPからの変更もBackendで拒否する。
  権限不足と機能停止を説明し分け、ユーザーの未保存入力を勝手に破棄しない。

## データモデルと移行案

- 設定の保存先は既存BackendのPostgreSQLとし、外部の有料機能管理サービスは追加しない。
- 組織ごとの固定キー・状態・version・更新者・時刻を持つモデルを候補とする。
  システム設定は組織境界と混同せず、運営APIだけから変更する。
- 既存組織は現在使える全機能を有効として移行し、既存データとRole/Permissionを保持する。
  未定義キーや不正値は拒否する。将来追加する機能の既定値は明示的なmigrationで決める。
- 機能の停止と再有効化はデータの削除・所属解除を伴わない。再有効化後は既存データを続けて利用する。
- 通常・デモ両DBへ同じschema migrationを適用する。
  匿名デモの機能初期値と破棄処理を合わせ、デモから運営設定を編集できないようにする。
- Neon runtime roleの権限拡大は行わない。既存のownerによるmigrationとアプリ用CRUDの分離を維持する。
  RLSの新規導入は今回の設計に含めない。

## 実装前の残確認と検証

1. 候補の機能単位・システム設定項目を確定する。機能間依存（例: 設計停止中の既存ケース実行）も明示する。
2. 各書き込み経路、コメント、リンク、添付、復元、間接作成、MCPのpreview/applyを一覧化し、必要な機能を対応づける。
3. 運営者のみ変更可、組織管理者は閲覧のみ、Project権限を増やさないことをAPIテストする。
4. 有効→無効→再有効で、read/export・write拒否・既存データ保持を確認する。
5. 無効化直前に作ったトークン・日程案・再送キーでも停止が効くことと、通常/デモの独立性を確認する。

この設計段階では設定値・権限・schema・公開環境を追加変更しない。
