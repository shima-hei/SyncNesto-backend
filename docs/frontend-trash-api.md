# ごみ箱・削除データの保持

Project内の要件定義書、セクション、要件、タスク、テスト設計書、ドキュメント、文書添付の論理削除行を扱う。通常データの復元期限は削除日時から30日（`DELETED_DATA_RETENTION_DAYS`、0は期限なし）。既存の `deleted_at` と版を使い、DB変更はない。

## API

- `GET /projects/{project_id}/trash`: `q` は名前のリテラル部分一致、最大200文字。`kind` は上記資源のsnake_case値。`page` 1–500、`page_size` 1–50、標準20。削除日の降順、種類・IDで安定順序。
- `POST /projects/{project_id}/trash/{kind}/{resource_id}/restore`: `{ "deleted_at": "2026-10-08T00:00:00Z", "version": 2 }`。添付は `version: null`。成功204。

一覧は種類、ID、名前、親のID、削除日時、保持期限、版、`can_restore`、`blocked_reason`を返す。本文・過去版・ストレージキー・署名URLは返さず、件数も権限で絞る。

認証・組織・有効なProject所属と `project:read` が必要。種類ごとに `read` と `delete` の両方を要求する。添付は既存の削除と同じ `document:read` + `document:update`。復元にはさらに種類の `update` が必要。運営管理者・組織所有者にも所属の省略はない。

親→対象の順でロックし、削除日時と版を照合する。再削除・版変更は409 `VERSION_CONFLICT`（`current` は概要のみ）、既に復元・回収済みなら404。保持期限以上または親が削除済みなら409。要件・セクションの親は要件定義書、文書添付の親はドキュメント。親を先に復元する。親を戻しても、個別削除された子は復元しない。

復元時は版を進め、文書には復元版の本文スナップショットも追加する。監査は `{kind}.restored`、本文は記録しない。通常の一覧・横断検索・関連・添付取得は復元後の状態を使う。

## 期限後の完全削除

既存の論理削除行にも元の削除日時から期限を適用する。導入時に既に30日を経過しているデータは復元不可・回収候補になるため、初回実行の前にdry-runで範囲を確認する。ファイルの実回収にはストレージ削除権限を持つ環境で実行する。

起動やHTTPリクエストで自動回収しない。同じBackend環境変数を設定し、まず `uv run python -m scripts.cleanup_deleted_data --tenant-id <ID>` で候補の種類・ID・削除日時を確認する。実回収には `--execute` が必要。1回20件、`--limit` 1–100。対象数は今回の候補数であり全体総数ではない。30日経過で復元を拒否し、物理削除はコマンド実行時に行う。定期回収を運用する場合は、このコマンドを運用者のジョブから実行する。

所有する子・履歴・添付・コメント・関連行も回収する。関連先の業務資源は残す。生存するタスクの親、要件のセクション、未決事項の関連要件は参照を解除して版を進める。監査ログは別の保持方針を維持する。分類されていない外部キー参照があれば、ファイル削除前に停止する。

文書添付とテスト証跡は、ストレージ削除成功後だけDB行を回収する。失敗では期限後の行を残し次回再試行する。期限後の復元を拒否するため、一部のファイルが回収済みでも復元可能とは表示しない。復元済み候補はロック後の再検証でスキップする。削除前に発行した署名URLは有効期限まで使える場合がある。

## 範囲とデモ

組織・ユーザー・Project自体、ボード・マイルストーン、単独のコメント・未決事項、テスト設計内の項目・因子・パターン、物理削除される関連解除は本ごみ箱の対象外。親資源の完全削除ではその所有行を回収する。削除済みProject内のデータは本コマンドの候補にも含めない。

デモは保持期間を延長しない。有効セッション中だけ復元でき、終了後は既存の全回収を行う。通常の回収コマンドは `APP_ENV=demo` では拒否し、通常環境でもデモ組織を候補から除外する。
