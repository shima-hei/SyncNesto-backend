# コメントのメンションAPI

対象は要件コメント、要件定義対象コメント、タスクコメント、テスト設計コメント。本文は従来のプレーンテキストを維持する。既存の認証、CSRF、対象所属確認、操作権限、投稿者制限、versionを使用する。

## 本文と出現位置

作成・本文編集・読み取りschemaに `mentions` を追加する。省略時は空配列。従来の `body` / `comment` の命名は変更しない。

```json
{
  "body": "😀 @田中 太郎 確認お願いします",
  "mentions": [
    { "user_id": 12, "start": 3, "end": 9, "display_name": "田中 太郎" }
  ]
}
```

`start` は開始位置、`end` は終了位置を含まない半開区間。単位はJavaScript文字列とTextareaの選択位置と同じUTF-16コード単位。絵文字など補助平面の文字は2単位。本文のtrimやUnicode正規化を位置確定後に行わないこと。

同一ユーザーの複数出現を許可する。最大100出現。区間の重複、本文範囲外、サロゲートペア途中、`@display_name` と本文の不一致を400で拒否する。新規出現の表示名は現在のユーザー名と一致する必要がある。改名済みの既存コメントを編集するときは、保存済みのユーザーと表示名の組み合わせを保持できる。名前変更で本文を自動書換えしない。

本文編集では配列全体を送る。削除された出現・対象ユーザーはDBから削除する。`mentions` を省略した本文更新は全関連を消去する。テスト設計の解決状態だけの更新は本文と関連を保持し、本文なしでのメンション更新は許可しない。

## 候補と権限

既存 `GET /projects/{project_id}/member-users` の `q`、`limit`、Avatar付きユーザー概要を使用する。任意の `mention_permission` パラメータを追加した。

| コメント | mention_permission |
| --- | --- |
| 要件、要件定義対象 | requirement:read |
| タスク | task:read |
| テスト設計 | test_plan:read |

指定時は、論理削除されていないプロジェクト所属と有効ユーザー、対象の閲覧権限を条件にする。システム権限で閲覧可能でも、候補にはプロジェクト所属が必要。未指定時のメンバー選択APIの挙動は維持する。検索は取得上限を適用する前に名前・メールで行う。

コメント保存でも同じ条件でuser_idを検証する。存在しないユーザー、プロジェクト外、退会、無効ユーザー、閲覧権限がないユーザーは400。投稿者の操作権限と対象の所属は既存Router/Serviceで確認する。退会済みユーザーへの保存済みメンションは読み取れるが、再保存時は削除または置換が必要。

## 永続化と将来の通知

`comment_mentions` は4種類の既存コメントへのnullable FKを持ち、CHECKで必ず1種類の親を指定する。親FKと `user_id` ごとにUNIQUEを設定。本文内出現は `occurrences` JSONBに位置と表示名のスナップショットを格納する。ユーザー識別はFKを正とする。

作成時の検証、対象確定を `CommentMentionService` に分離する。本文と関連は同一commit。編集は既存関連を再利用し、不要な関連を除去する。コメントの論理削除時も関連を除去し、物理削除はFK CASCADEで除去する。

通知は将来この一意な関連を参照する。本文解析や出現数に依存しない。通知生成時は編集前後の対象差分、メンバーと権限の再確認、同一コメント・ユーザーへの重複防止、commit後の配送を別責務として設計する。今回は通知生成・通知UIを追加していない。

## マイグレーションと互換性

`73c08ecae547_add_comment_mentions.py` を追加。既存本文の変換やバックフィルは不要。古い `@名前` を自動で関連にしない。旧クライアントの作成は従来どおり動作するが、旧クライアントで本文を編集すると関連を失うため、FrontendとBackendは合わせて更新する。

```bash
uv run alembic upgrade head
uv run pytest tests/routers/test_comment_mentions.py
```
